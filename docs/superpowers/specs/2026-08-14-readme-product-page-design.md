# README 产品页改版设计

## 目标

将 `kang-frontend-standard` 的公开 README 从简要仓库说明升级为可扫描、可验证、可安装的 Skill 产品页。README 面向第一次发现这个仓库的人，优先回答：它解决什么问题、安装后得到什么、如何安装验证、有什么真实证据、哪些能力仍未验证。

本次改版采用“叙事主张 + 证据结构”：用有记忆点的价值主张建立设计气质，用证据优先的信息结构降低理解和安装成本。

## 不变的边界

- 不修改 `SKILL.md` 的运行规则或触发边界。
- 不把 `SKILL.md` 原样复制到 README。
- 不把概念稿、静态预览、本地验证或模拟流程包装成生产能力。
- 不包含任何第三方个人 Profile、姓名、头像、社交账号、品牌、Logo、私有素材或固定审美禁令。
- 不在 README 中写入 API Key、Cookie、Token、私有路径或用户个人信息。
- 不强制 React、Tailwind、shadcn、固定字体、固定配色或固定页面结构。

## 信息架构

### 1. 首屏

价值主张建议为：

> 让 AI 做前端时，不再只是“能运行”，而是先判断、再设计、再验证。

首屏同时提供：适用范围、`npx skills add` 安装入口、当前版本、MIT 许可证和真实案例入口。首屏采用浅色留白、细边界和一张完整案例图；不使用缩略拼盘，也不把案例概念图伪装成生产截图。

### 2. 案例证据

至少展示两组本地真实测试证据：装修咨询入口和案例集页面。每个案例说明原始问题、Skill 介入点、用户认可的改进，以及仍然待验证的能力。

案例素材应标明证据级别：`tested locally`、`prototype`、`simulated` 或 `to verify`。若截图依赖动效，应在稳定状态捕获，并单独说明动效是否被验证。

### 3. 安装前后对照

用短表说明没有 Skill 与使用 Skill 的差异，覆盖项目识别、成熟参考、动效判断、浏览器检查和迭代记录。避免宣称“必然更惊艳”，只描述可观察的流程与交付差异。

### 4. 能力矩阵

以用户结果为中心展示十项能力：视觉方向、成熟参考、选择性优化、字体与层级、组件与 Token、动效、响应式、无障碍、性能、测试与部署。长判断留在 `SKILL.md` 和引用文件中。

### 5. 安装、前置条件与排错

提供标准安装命令和公开发现验证命令：

```bash
npx skills add KanG-ciyuan/kang-frontend-standard
npx skills add KanG-ciyuan/kang-frontend-standard --list
```

前置条件只记录支持 `SKILL.md` 的 Agent、Node.js / `npx` 和浏览器检查所需的本地服务。Troubleshooting 至少覆盖：找不到有效 Skill、公开仓库无法发现、浏览器预览打不开、外部参考不可访问、动效未完成就截图、本地验证不等于生产部署。

### 6. 版本、边界与英文区

增加当前版本与变更摘要，明确 `verified`、`simulated`、`to verify` 证据边界，说明结果依赖模型、素材和运行环境。英文区提供独立的价值主张、安装命令、核心能力、证据边界和 License，不做机械逐句翻译。

## 视觉与写作原则

- 首屏先讲用户结果，再讲实现方式。
- 使用真实截图、完整页面链接或可复现命令作为证据。
- 每段尽量只承载一个判断，使用表格、折叠区和短列表降低阅读负担。
- 视觉上保持克制、清晰和可扫描，不用装饰性渐变、无目的动效或过大的标题掩盖证据不足。
- 可以借鉴公开 Skill README 的产品化结构，但公开内容只呈现 Kang 的职责、案例、判断和证据边界。

## 作者身份规则

- README、Skill、仓库描述和发布说明只将 Kang 标识为创建者、维护者和发布者。
- 不放置其他个人的姓名、头像、社交链接、个人简介、二维码、Profile 组件或致谢文案。
- 可以概括“参考了公开的设计系统、组件库和开源项目”，但不把第三方个人身份写入公开页面。
- 本仓库只包含 Kang 自己的规则与实现，不直接复制第三方代码；因此不新增第三方作者署名或版权声明。

## 实施与验证

1. 保留当前 `SKILL.md`、版本和仓库身份不变，只重写 README。
2. 整理装修咨询与案例集的完整截图和链接；没有可公开的素材时使用明确占位，不伪造截图。
3. 本地运行 README 结构检查、敏感信息扫描和 Markdown 链接检查。
4. 使用 `npx skills add ... --list` 验证公开发现；完整隔离安装另行记录结果。
5. 检查 README 是否仍然存在私有路径、密钥、未经验证的能力声明或“复制 SKILL.md”问题。
6. 通过功能分支和 PR 发布，不直接推送默认分支。

## 成功标准

- 陌生读者能在首屏理解价值、安装方式和证据入口。
- README 具有真实案例和明确证据等级，而不是只有功能描述。
- 读者能区分首次开发、二次开发和持续迭代的适用范围。
- 安装、前置条件和常见失败路径可操作。
- README 的内容更完整，但没有把视觉设计写死成固定页面模板。
- 所有公开声明都能对应到仓库内容、测试结果或明确的待验证状态。
